# Архитектура системы (SkyMP Heavy RP)

*[Português](ARCHITECTURE.md) · [English](ARCHITECTURE.en.md) · **Русский** · [Español](ARCHITECTURE.es.md)*

Сервер SkyMP Heavy RP работает на распределённой архитектуре: критичные сервисы разделены, чтобы обеспечить безопасность, стабильность и строгое следование правилу **власти сервера**.

## 1. Топология сервера

Инфраструктура делится на следующие модули:

### 1.1 База данных (MariaDB/MySQL)
**MariaDB** — абсолютный источник истины. К ней подключаются все сервисы.
- **Основные таблицы:** `accounts`, `characters`, `character_inventory`, `audit_logs`, `whitelist_applications`, `staff_roles`, `factions`, `holds`, `properties`, `market_stalls`, `crafting_recipes`, `crafting_ingredients`. Полная схема — в `skymp/packages/database/schema.sql` плюс миграции `v2`–`v16`, применяемые **по порядку** (v6 = `launch_tickets`, v7 = индексы горячих запросов, v8 = `game_sessions`, v9 = `characters.gold`, v10 = Родство Души, v11 = журнал институциональных казначейств, v12 = журнал регионального рынка, v13 = идемпотентность продаж торговых точек, v14 = Inventory Framework, v15 = Economy Framework, v16 = заглушение голоса администрацией, переживающее рестарт).
- Некоторые таблицы есть в схеме, но их не читает никакой активный код (`store_purchases`, `trade_routes`, `magic_licenses`, `magic_violations`, `character_diseases`, `staff_permissions`) — они принадлежат PARKED-модулям (см. 1.4).
- **Жёсткое правило:** ни одно изменение игрового состояния (деньги, позиции, предметы) не происходит без записи в MariaDB или чтения из неё. Node.js не доверяет данным, долго живущим в памяти без сохранения.

### 1.2 Веб-приложение и API (`apps/web`)
Сделано на **Express.js / Node.js**.
- Отдаёт веб-панель (вайтлист, администрация, профили вне игры).
- Отдаёт **лаунчеру** обмен Discord OAuth (`POST /api/launcher/oauth/exchange`, который также выпускает тикет запуска) и принимает краш-репорты. Манифест модов приходит **не** отсюда — он из `apps/game-api` и GitHub Releases (см. 1.3.1 и `LAUNCHER_DISTRIBUTION.md`).
- Аутентификация обязательна, через `passport-discord`.
- Не путать с **внутриигровой панелью игрока** (см. 1.4.2), которая работает внутри HUD самого SkyMP, а не в браузере.
- **Заявка на персонажа** (`/api/apply`, `apply.html`): помимо имени и биографии собирает `motivations`/`weaknesses`/`social_ties` (рубрика вайтлиста Heavy RP — см. `SKYMP_RP_DEVELOPMENT_PLAN.md` §8.1). Эвристика по ключевым словам (`detectsStrongConcept` в `server.js`) выставляет `characters.needs_extra_review` для сильных концептов (знать, вампиризм, ликантропия, даэдра, лидерство во фракции) — это не автоматический запрет, а сигнал администрации смотреть внимательнее; администрация может приложить `extra_review_notes` через панель (`PATCH /api/whitelist/:id`). `skymp/gamemode/whitelist.js` читает `characters` с `ORDER BY id DESC LIMIT 1` при разрешении спавна.

### 1.2.1 Мастер-API (контракт SkyMP, обслуживается `apps/web`)
`GET /api/servers/:masterKey/sessions/:session` → `{ user: { id, discordId } }`

Этот эндпоинт мы не выдумывали: его вызывает сервер SkyMP, когда `offlineMode: false` (см. `skymp5-server/ts/systems/login.ts` в upstream). `user.id`, который мы отвечаем, **становится `profileId`** игрового режима.

Это та деталь, которая забирает личность из рук клиента. При `offlineMode: true` клиент сам объявляет свой `profileId` в `skymp_config.json`, и сервер верит — любой правит файл и становится другим человеком. При `offlineMode: false` `profileId` приходит отсюда, от того же сервиса, который аутентифицировал Discord и одобрил вайтлист.

Стандартный `master` у SkyMP — `https://gateway.skymp.net`; направить его на нашу панель — это одна строка в `server-settings.json`. `masterKey` должен совпадать с обеих сторон (`MASTER_KEY` в `.env` панели).

Сессии живут в `game_sessions`, хранятся как SHA-256 хеш, с `expires_at`, `revoked_at` (мгновенный бан, не дожидаясь TTL) и `resolve_count` (высокое значение намекает на сессию, поделённую между машинами).

### 1.3 Бот Discord (`apps/bot-discord`)
Сделан на **discord.js**.
- Связывает аккаунт Discord с игровым `profileId` (`POST /api/sync-role`, вызывается веб-панелью при одобрении/отклонении вайтлиста).
- **Временные голосовые каналы** (`voiceChannels.js`, команды `/voz-criar <имя>` и `/voz-fechar`, только для администрации): практичная альтернатива голосу, пока нативный внутриигровой VOIP (`/voz`, см. 1.4.4) никем не был услышан. Патч клиента, существовавший ради этого, **отброшен** (`docs/technical/VOICE_CLIENT_PATCH.md`); путь захвата, который есть сегодня, — нативный помощник WASAPI вне CEF (`docs/technical/VOICE_NATIVE_HELPER.md`), а общее состояние голоса — в `docs/technical/SKYVOICE_PRODUCTION_READINESS.md`. Канал удаляется автоматически примерно через 30с после того, как опустеет. Команды регистрируются при старте бота (`deploy-commands.js` выполняется по событию `ready`); сбой там не роняет бота, но громко пишет в лог. `npm run deploy-commands` остаётся для ручного запуска.
- **Лог модерации** (`moderationLog.js`, внутренний эндпоинт `POST /api/moderation-log`): публикует embed в настраиваемый канал (`MODERATION_LOG_CHANNEL_ID`) при каждом действии модерации. Это было изначальное намерение, записанное здесь, и годами оставалось нереализованным; появилось 07.08.2026.

  **Канал — это не запись, а уведомление.** Записью остаётся `audit_logs`, которую пишут геймод и панель в том же потоке, что и само действие, до того как что-либо уйдёт в Discord. Это различие определяет поведение при сбое: если Discord недоступен, действие модерации всё равно происходит, ничего не откатывается и ничего не замедляется. Эндпоинт отвечает **202 до** обращения к Discord, и ни один производитель события не ждёт отправки.

  | Событие | Производитель | Источник |
  |---|---|---|
  | `kick` | `admin-service.kickPlayer` (`/kick`) | `gamemode` |
  | `permakill` | `admin-service.retireCharacter` (`/permakill`) | `gamemode` |
  | `whitelist_approve` / `whitelist_reject` / `whitelist_reset` | `apps/web` `PATCH /api/whitelist/:id` | `painel` |
  | `ban` | **нет** — см. ниже | — |

  **`ban` объявлен и не имеет производителя.** `ban` — это право, которое роли `admin` и `owner` выдают в `admin-service.js` и которое **не использует ни одна команда**: `/ban` нет ни в геймоде, ни в панели. Тип события остаётся объявленным (с тестом, фиксирующим его форму), чтобы в день появления команды это стоило одной строки — но лог не выдумывает действие, которого у сервера нет.

  **Почему push, а не опрос `audit_logs`.** У бота есть `mysql2` в `dependencies` без использования, так что читать таблицу было возможно. Отвергнуто: это дало бы учётные данные базы третьему процессу для чтения того, что он не пишет, в обмен на задержку опроса. Push уходит оттуда, где происходит действие, и единственный секрет, который пересекает границу, — `INTERNAL_API_SECRET`, который панель уже разделяет с ботом. Геймод использует `http.request` из ядра, а не `fetch`: версия Node, встроенная в SkyMP, нам не подконтрольна, а глобальный `fetch` существует только с Node 18.

  **Пустой канал отключает отправку.** Без `MODERATION_LOG_CHANNEL_ID` эндпоинт всё равно отвечает 202 и ничего не публикует; без `BOT_INTERNAL_URL`/`INTERNAL_API_SECRET` в `.env` геймода геймод даже не пытается. Сервер, которому канал не нужен, ничего не платит и не видит ошибок. Канал должен быть закрытым для стаффа: embed несёт причины кика и заметки ревью вайтлиста.

  Протестировано с замоканным `discord.js` (21 тест), в том же стиле, что и 19 уже существовавших. Не покрыто: публикация в настоящий канал, для которой нужны реальные бот и гильдия.

### 1.3.1 Game API (`apps/game-api`)
Express, порт `GAME_API_PORT` (7758) — тот самый порт, который лаунчер всегда вызывал и для которого не было сервера. Подробности в `docs/technical/LAUNCHER_DISTRIBUTION.md`.
- **`GET /mods.json`**: манифест паритета модпака (`{mods, loadOrder}`), генерируется офлайн скриптом `scripts/generate-mods-manifest.js` из эталонной папки `Data/`. Отсутствующий или битый манифест отвечает **503**, но никогда пустым списком — пустой список прошёл бы проверку лаунчера и пустил бы любой модпак.
- **Очередь** (`POST /api/queue/join`, `POST /api/queue/status`): фиксированная вместимость, FIFO, с истечением брони, чтобы тот, кто закрыл лаунчер после допуска, не держал слот вечно. Аутентифицируется одноразовым тикетом, выпущенным панелью (`launch_tickets`, миграция v6) — `discordId` публичен и доказательством личности не является.
- **Игровая сессия**: при допуске пишется строка в `game_sessions` (миграция v8), а токен возвращается лаунчеру, который записывает его как `session` в `skymp_config.json`. Именно этот токен сервер SkyMP разрешает через мастер-API (см. 1.2.1) — так личность перестаёт быть заявлением клиента.
- **`POST /internal/session/resolve` / `/release`** (`X-Internal-Secret`): освобождение слота при отключении. `resolve` стал избыточным после появления нативного пути сессии — оставлен только на время, пока тест в игре не подтвердит поток мастер-API.

### 1.4 Нативный сервер SkyMP (игровой режим)
Находится в `skymp/gamemode/`.
- Выполняется на Node.js с внутренними библиотеками SkyMP (`mp.events`, `mp.players`).
- Ведёт жизненный цикл игрока: подключение, отключение, спавн, бой, команды чата и сохранение предметов в реальном времени.
- Делегирует бизнес-правила сервисам, активным сегодня (`governance-service.js`, `market-stalls-service.js`, `death-service.js`, `player-panel-service.js`, `voip-service.js`, `soul-service.js`, `trade-service.js`, `nametag-service.js`). Ещё **пять** сервисов лежат на диске (`economy-regional.js`, `crafting-service.js`, `jobs-service.js`, `housing-service.js`, `horse-service.js`), но они **PARKED** — никогда не регистрируются в `core/module-registry.js`, а значит никогда не работают в продакшене (см. комментарий в `phase0-basic.js`). `trade-service` покинул этот список 13/08/2026, когда начал работать поверх Inventory Framework (`docs/framework/INVENTORY_FRAMEWORK.md`). Ещё пять (`economy-service`, `justice-service`, `faction-service`, `survival-service`, `disguise-service`) были **удалены** за дублирование активных систем или небезопасность — см. `docs/technical/PARKED_SERVICES_DECISION.md`.
- Модули регистрируются и включаются/выключаются через `core/module-registry.js` (флаги `ENABLE_*` в `.env`), который также разрешает зависимости между модулями и автоматически регистрирует команды в `core/command-registry.js`.
- **Конфигурация геймплея** приходит из `skymp/config/server-options.<env>.json`, загружается и валидируется через `core/server-options.js`. Действуют только опции из `SPEC` того файла — загрузчик предупреждает при старте, если находит ещё не реализованную опцию, и **прерывает загрузку**, если значение неверного типа или вне диапазона. См. `docs/technical/SERVER_OPTIONS_SCHEMA.ru.md`.
- **Домен «Родство души»** в `core/soul.js` — генератор с фиксированным бюджетом, полосы, зерно, выведенное из одобренной заявки, и разрешение в четыре исхода. Это **чистая функция**: без базы, без `mp`, без побочных эффектов. Именно поэтому он появился раньше сервиса — его можно доказать вне сервера, и именно здесь ошибка обходится дороже всего потом. Проект в [`docs/design/SOUL_AFFINITY.md`](design/SOUL_AFFINITY.md) (на португальском); **сервис**, который говорит с миром (знаки, метки, дерево), по-прежнему заблокирован тестом в игре.
- **Типизация API `mp`**: `skymp/gamemode/types/mp.d.ts` (SkyMP не публикует типов). `npm run typecheck` носит справочный характер — игровой режим остаётся чистым JS, который сервер грузит напрямую, без шага сборки.

#### 1.4.1 Мост интерфейса (CEF)
Связь между игровым режимом и CEF-интерфейсом (`skymp/ui/`) использует два свойства SkyMP, зарегистрированных в `phase0-basic.js`:
- **`browserModal`**: канал разовых модальных окон (например, меню взаимодействия управления). `updateOwner` выполняет `ctx.sp.browser.executeJavaScript('window.handleServerModal(...)')` на клиенте.
- **`panelData`**: выделенный канал панели игрока в формате `{ channel, data }` — клиент направляет это в `window.handlePanelData(...)`, и каждая вкладка (`status`, `governance`, `economy`, `social`) рисует свой блок.

В направлении интерфейс→сервер `mp.onUiEvent` направляет каждое событие через `core/ui-event-router.js`, который маршрутизирует по префиксу `uiEvent.type` (например, `governance:*` → `governance-service.js`, `panel:*` → `player-panel-service.js`). Новым модулям, которым нужен интерфейс, достаточно вызвать `uiEventRouter.register('<префикс>', handler)` в своём `initialize()` — править `phase0-basic.js` под каждый новый тип события не нужно.

С 11.08.2026 `core/ui-event-gateway.js` владеет глобальным callback и проверяет envelope до маршрутизации; `core/ui-event-rate-limiter.js` измеряет и при настройке ограничивает объём по актёру и типу события. `core/connection-monitor.js` отвечает за polling, переподключение и отмену устаревших ответов whitelist. `core/opaque-credential.js` централизует генерацию, хеширование и редактирование непрозрачных учётных данных. В экономике `core/institutional-treasury-service.js` и `core/regional-market-transaction-service.js` объединяют баланс, склад и ledger в одной транзакции; миграция v13 делает повторы покупок идемпотентными. Эти границы покрыты тестами, а PARKED-модули по-прежнему не включены в boot.

#### 1.4.2 Панель игрока (в игре)
`player-panel-service.js` — модуль `player-panel` (`ENABLE_PLAYER_PANEL_SERVICE`), открывается командой `/painel`. Не дублирует бизнес-логику: только агрегирует чтения из уже существующих сервисов.
- **Статус**: здоровье/магия/запас сил читаются через `mp.callPapyrusFunction('method', 'Actor', 'getActorValue', ...)` (тот же приём, что и в `death-service.js`), золото — через `core/transaction-service.js`, RP-состояние — через `core/character-state.js`. Обновляется опросом каждые 2с, пока панель открыта, и переотправляется только при изменении значения.
- **Управление**: `governance-service.getMyGovernanceSummary()`.
- **Экономика**: `market-stalls-service.getMyEconomySummary()`.
- **Социальное**: собственный список `character_known_identities` персонажа.
- Интерфейс в `skymp/ui/player-panel.css` / `player-panel.js`, визуально повторяет [Prisma UI](https://prismaui.dev) (чёрная стеклянная карточка, фиолетовое свечение, чип статуса, навигация «таблетками» с рунами Старшего Футарка как иконками вкладок).
- **Проактивное обновление**: `core/panel-refresh-bus.js` — развязанный `EventEmitter`. `governance-service.js` вызывает `panelRefreshBus.requestRefresh(actorId, 'governance'|'status')` после штрафа, ордера или ареста, а `player-panel-service.js` (единственный подписчик, регистрируется в `initPlayerPanelService`) переотправляет нужную секцию, **только если панель у того игрока уже открыта**. Существует, чтобы `governance-service.js` не пришлось зависеть от `player-panel-service.js` (который уже зависит от него), и при этом панель не открывалась сама собой на экране игрока.
- **Прямое действие на вкладке «Социальное»**: у каждого знакомого есть кнопка «Дать прозвище», открывающая встроенную мини-форму (`skymp/ui/player-panel.js`, `socialRow`/`bindSocialRenameHandlers`) и отправляющая `panel:social:rename` с `{ targetCharacterId, alias }`. `player-panel-service.renameKnownPerson` вызывает `identity-service.upsertKnownIdentity` напрямую по characterId — работает даже когда цель отключена, поскольку `character_known_identities` не зависит от активного actorId.

#### 1.4.3 Смерть и последствия (`death-service.js`)
Модуль `death` (`ENABLE_DEATH_SERVICE`), фаза `lab`. Существует, чтобы «умереть» имело механический и социальный вес, а не было пустым событием — ключевой принцип Heavy RP из `SKYMP_RP_DEVELOPMENT_PLAN.md` (§8.1, «Смерть и последствия»).
- Смерть → `core/character-state.js` переходит в `DOWNED`, что само по себе блокирует геймплей/бой/речь через `core/action-policy.js` без дополнительной работы. Основной триггер — нативный хук **`mp.onDeath(actorId, killerId)`**, срабатывающий в кадр смерти; опрос каждые 2с остаётся страховкой, пока хук не подтверждён в реальной сессии (`handlePlayerDowned` идемпотентен по персонажу, так что оба пути вместе ничего не дублируют). **Хук принадлежит `core/death-events.js`**, а не `death-service`: небольшая именованная шина по образцу `panel-refresh-bus`, которая присваивает `mp.onDeath` ровно один раз и раздаёт событие именованным подписчикам, каждый из которых изолирован `try/catch`. Она существует потому, что прямое `mp.onDeath = ...` — это исключительное владение: второй модуль, которому понадобился бы тот же события, стёр бы первый **молча**, а опрос замаскировал бы потерю задержкой в две секунды. Второй потребитель уже предусмотрен (`hunting-service`, см. [`HOSTILE_MOB_ACTIVATION_DECISION.md`](technical/HOSTILE_MOB_ACTIVATION_DECISION.md) §7.3).
- **Авторство**: `mp.onDeath` отдаёт `killerId` — кто убил, `0` когда автора нет. Пишется в `audit_logs` как `death:killer` и переносится до истечения кровью, которое случается минутами позже. Это именно атрибуция — в отличие от близости из `logDeathContext`, которая обстоятельна: в драке впятером появляется пять имён, и администрация решает на глаз.
- **Помощь**: `/socorrer <actorId>` (любой игрок, в пределах `RESCUE_RANGE`) останавливает кровотечение и стабилизирует цель обратно в `NORMAL` с частичным здоровьем (`STABILIZE_HEALTH`). Дистанция проверяется через `core/range-utils.js` (вынесен из `governance-service.js`, используется обоими).
- **Истечение кровью**: если никто не помог за `BLEED_OUT_MS` (4 мин), персонаж становится `DEAD`, применяется штраф золотом через `core/transaction-service.removeGold` (атомарно — никогда не оставляет отрицательный баланс), и только тогда происходит респавн в обычной безопасной точке.
- **Доказательства против RDM**: в момент истечения кровью `logDeathContext` пишет в `audit_logs` (`action='death:context'`) снимок того, кто был рядом (тот же радиус близости, что у чата `say`) — это обстоятельство, а не атрибуция. Атрибуция того, кто убил, приходит из `killerId` в `mp.onDeath` (см. выше); снимок близости остаётся полезен, потому что показывает **кто был на сцене**, а это тот вопрос, который администрация задаёт при групповой жалобе на RDM.
- Каждый переход (`DOWNED`/спасён/оштрафован/возрождён) вызывает `panelRefreshBus.requestRefresh(actorId, 'status')`, отражаясь в `/painel` в реальном времени.
- **Минимальный RP-слой для боя**: надёжного нативного хука «кто кого атаковал» в этой базе нет, поэтому область — доказательства, а не принуждение. `/iniciar <actorId> <причина>` пишет явную отметку открытия IC-конфликта в `audit_logs` (`combat:initiate`). Параллельно тот же опрос HP, который ловит `DOWNED`, каждый тик выполняет `checkDamageSpike` — падение здоровья `>= DAMAGE_SPIKE_THRESHOLD` (эвристика, 25 пунктов) за один тик в 2с запускает `logDeathContext(..., 'damage_spike')`, создавая след близости даже когда никто не пользуется `/iniciar`. В `core/range-utils.js` появился `nearbyActors()`, чтобы не дублировать логику обхода соседей между контекстом смерти и контекстом урона.

**Перманентная смерть (мягкое удаление):** `admin-service.retireCharacter(actorId, targetActorId, reason)`, команда `/permakill` (право `retire_character`, только уровни `admin`/`owner` — никогда модератор). Никогда не делает `DELETE` — только `UPDATE characters SET status='retired'`, с обязательной причиной и записью в аудит. `whitelist.js` разрешает спавн только при `status='approved'`, поэтому персонаж со статусом `retired` больше никогда не войдёт в игру, и никаких других изменений для этого не нужно.

#### 1.4.4 Голос по расстоянию (`voip-service.js`)
Модуль `voip` (`ENABLE_VOIP_SERVICE`), фаза `lab`. Сигнализация WebRTC (offer/answer/ICE) по собственному WebSocket (порт `VOIP_PORT`, по умолчанию 7778) — сам звук идёт P2P между клиентами после рукопожатия, сервер лишь обменивается сигнализацией и считает громкость по расстоянию каждые 2с. Радиусы берутся из `core/proximity-ranges.js` — единого источника и для чата, **и** для голоса: раньше две таблицы расходились (голос шептал на 200, чат на 450), так что один и тот же жест «подойти ближе, чтобы говорить тихо» работал или нет в зависимости от канала.

**С 07.08.2026 есть второй путь, и именно он останется.** Описанный выше P2P WebRTC никогда не давал звука: CEF клиента отклоняет `getUserMedia`, а флаг Chromium, который это разрешал, был *намеренно удалён* в SkyrimPlatform 2.1 — его возврат открыл бы микрофон игрока любому серверу SkyMP, к которому он подключится позже. Теперь нативный хелпер (`voice-helper/`) захватывает звук вне браузера и шлёт `audio_frame` по тому же сокету с тем же тикетом; сервер **ретранслирует** по близости с приложенной громкостью, переиспользуя результат 2-секундного тика, а браузер только воспроизводит. Это заодно решает NAT/CGNAT, который сломал бы P2P-сетку. Оба пути сосуществуют: фаза 2 убирает старый. См. [`technical/VOICE_NATIVE_HELPER.md`](technical/VOICE_NATIVE_HELPER.md).

**До этой правки функция существовала только на бумаге** — ничто в `phase0-basic.js` не вызывало `startVoipServer()`, а клиентский слушатель `mp.events.add('voip:connect', ...)` никогда не срабатывал, потому что нигде в игровом режиме серверный код не делает `mp.trigger`/emit этого события. Это не был видимо сломанный индикатор (чип статуса имеет `display:none`, пока не отработает `setStatus()`, а этого не происходило) — функция просто отсутствовала, молча.

- **Подключение по желанию через `/voz`** (не принудительно — и с 07.08.2026 **нативный голос не является обязательным условием запуска**: решение закрыто в §13 `SKYMP_RP_DEVELOPMENT_PLAN.md`, где этот модуль отнесён к необязательным и к этапу после Альфы, а реальным решением для Альфы и закрытой Беты названы голосовые каналы Discord (1.3)). Команда вызывает `requestVoiceConnection`, который выпускает одноразовый тикет (`issueTicket`, TTL 30с) и отправляет клиенту `{actorId, ticket, host, port}` через свойство `voipTicket` (тот же проверенный приём, что у `browserModal`/`panelData`).
- **Аутентификация по тикету**: рукопожатие WebSocket (`{type:'auth', actorId, ticket}`) требует, чтобы тикет совпал с выданным для этого `actorId` — без этого любой процесс, подключившийся к `ws://127.0.0.1:7778`, мог заявить чужой `actorId` и угнать его голосовой слот. Тикет расходуется при первом использовании (повтор не проходит).
- **Динамический хост**: поскольку `skymp/ui/index.html` — статический файл без шаблонизации, он сам не может знать публичный IP сервера, поэтому сервер шлёт `host`/`port` прямо в полезной нагрузке тикета (`VOIP_PUBLIC_HOST`/`VOIP_PORT` в `.env`), вместо жёстко зашитого у клиента `ws://127.0.0.1:7778` (который работал только когда игрок и сервер на одной машине).
- `VOIP_BIND_HOST` (по умолчанию `127.0.0.1`) задаёт, на каких интерфейсах слушает `WebSocketServer` — не путать с `VOIP_PUBLIC_HOST`, который клиент получает для подключения.
- **Путь отказа — часть замысла, а не остаток.** В официальном клиенте `getUserMedia` возвращает `NotAllowedError` (см. `docs/technical/VOICE_CLIENT_PATCH.md`), и именно с этим игрок столкнётся, пока решение §13 не пересмотрят, — то есть это обычный путь, а не исключение. `skymp/ui/index.html` закрывает сигнализацию и показывает причину в двух местах: чип статуса (состояние) и `chat-log` (причина, со ссылкой на `/voz-criar` в Discord). `onclose` не должен затирать уже показанную терминальную причину — сам по себе он написал бы «VOZ DESCONECTADA», что читается как нестабильность сервера и отправляет игрока заводить не тот тикет.

#### 1.4.5 Доказательства боя (`core/hit-events.js`)
Это не модуль registry, а слой, который потребляет `death-service`. Происходит из Red House (`docs/technical/REFERENCE_STUDY_SKYMP_RED_HOUSE.md` §4.1), с указанием лицензии в шапке файла.

- **Механизм**: `mp.makeEventSource('_onHitReported', <snippet>)` внедряет в клиент фрагмент, который слушает `ctx.sp.on('hit', ...)` из Skyrim Platform и сообщает `{target, aggressor, isPowerAttack, isSneakAttack, isBashAttack, isHitBlocked}`. Он существует потому, что SkyMP **отказался** отдавать пакет удара геймоду (issue #1338) — событие восстанавливается на стороне клиента.
- **Это доказательство, а не enforcement, и это центральное решение.** Red House пересчитывает урон из этого события и пишет его в ActorValue; здесь такого нет и появиться не должно. Событие присылает машина самого игрока, а `CONTRIBUTING.md` §3.6 говорит прямо: клиентское событие — это *«подсказка, а не доказательство»*. Решать по нему урон значило бы отдать бой тому, кто контролирует клиент. Сама записанная строка несёт `origem: 'cliente (makeEventSource) — evidencia, nao prova'`, чтобы никто не принял её за доказательство в разборе.
- **Агрегирует в эпизоды, а не пишет удар за ударом.** Эпизод открывается на первом ударе между парой `агрессор:цель` и закрывается по тишине (`JANELA_MS`, 10 с без нового удара); только тогда `death-service` пишет одну строку в `audit_logs` (`action='combat:episode'`) с количеством, типами ударов и длительностью. Одна драка даёт десятки событий — запись по удару сделала бы таблицу бесполезной именно тогда, когда она нужнее всего.
- **Отбрасывает урон самому себе** (`агрессор === цель`): падение, яд и дружественный огонь собственного заклинания — не агрессия между людьми и к разбору RDM отношения не имеют. Потолок `MAX_GOLPES_POR_EPISODIO` (200) — дальше точное число перестаёт иметь значение.
- **Клиентский фрагмент намеренно держат коротким**, и он глотает собственные ошибки: он работает в игровом цикле на чужой машине, без удалённой отладки, и его падение убило бы след всех последующих ударов того игрока. Агрегация, throttling и решение остаются на сервере.
- **Заменяет `checkDamageSpike`** из `death-service` (см. 1.4.3), который считает агрессией любое падение здоровья на 25 за тик в 2 с — он не отличает бой от падения со скалы и не знает, кто ударил. **Сегодня они сосуществуют**; эвристика уйдёт только тогда, когда Фаза 0 подтвердит, что событие доходит.
- **Статус проверки**: `mp.makeEventSource` подтверждена на реальном сервере (загрузка регистрирует событие), но **клиентский фрагмент никогда не выполнялся** — он запускается только когда кто-то подключается. Это Фаза 0 (`FASE_0_ROTEIRO.md`, этап 9).

#### 1.4.6 Проверка предмета по плагинам (`core/espm.js`)
`mp.lookupEspmRecordById(baseId)` позволяет серверу читать записи загруженных ESM, так что можно проверить, существует ли `base_id` и действительно ли это предмет, — вместо того чтобы писать в инвентарь любое число. Найдено при изучении Red House; **формат ответа прочитан с реального сервера, а не выведен по догадке.**

- **Подключено в двух точках, где в систему попадает новый `base_id`**: `/additem` и выставление товара в лавке. В обеих значение вводится руками в шестнадцатеричном виде, и до этого ошибочная цифра всё равно писалась в `character_inventory` — предмет никогда не появлялся в игре, но занимал строку в базе и в ledger, и никто этого не замечал, пока кто-нибудь не проверял инвентарь вручную. В лавке хуже: человек платит за строку, которая никогда не станет предметом на экране.
- **Деталь, на которой ошиблась бы реализация по догадке**: неверный FormID возвращает `{}` — пустой и при этом **truthy** объект, — поэтому `if (r)` пропустил бы Player как предмет. Правильная проверка — `r && r.record`, и на это есть мутационный тест.
- **Список разрешённого, а не запрещённого**: `TIPOS_DE_INVENTARIO` (`WEAP`, `ARMO`, `MISC`, `ALCH`, `AMMO`, `BOOK`, `INGR`, `KEYM`, `SLGM`, `SCRL`, `LIGH`). Опечатка в FormID попадает в любую запись игры — ячейку, квест, звук, перк, — и правильный вопрос здесь «это предмет?», а не «это одна из тех вещей, которые я вспомнил запретить?».
- **Пропускает, когда не может знать.** Если API нет (старый сервер, тестовая среда) или он упал, ответ помечается `indisponivel`, и `pareceItem` отвечает `ok`. Отказ выдаётся только если API ответил **и** ответил, что этот FormID не предмет, — иначе проверка стала бы способом сломать `/additem`, а не диагностикой. **Это проверка опечаток, а не полномочие** — тот же выбор, что и в 1.4.5, по той же причине.
- **Кэш** по `baseId`, хранит только `type` и `editorId`: сырой ответ несёт все поля записи в байтах, а load order в рантайме не меняется.
- Сигнатура описана в `types/mp.d.ts` с пометкой `[USO]` и указанием происхождения.

#### 1.4.7 Безопасные зоны (`core/safe-zones.js`)
`core/action-policy.js` начинает блокировать **по месту**, а не только по состоянию персонажа. Происходит из Red House, который перед нанесением урона проверяет свойство `isInSafeLocation`.

- **Отвечает, где человек находится и что это место запрещает.** `zoneOf(actorId)` читает `mp.get(actorId, 'locationalData')` и сопоставляет с конфигом; `blocksCategory` отвечает по категории из `action-policy`. `canPerform` получила это измерение через `context`, который уже был объявлен «для будущих проверок».
- **Правило обеих сторон**, с отдельным тестом: действие между двумя людьми блокируется, если защищён **любой** из них (`blocksBetween`). Защита только цели позволила бы стрелять изнутри зоны наружу.
- **Состояние проверяется раньше места.** Для того, кто в наручниках внутри безопасной зоны, полезное объяснение — *«вы в наручниках»*.
- **Список зон рождается пустым.** Конфиг в `skymp/config/safe-zones.json`; при его отсутствии или при `enabled !== true` модуль отвечает «зон нет вообще», и ничего не меняется — тот же шаблон, что у `npc-cleaner`, и по той же причине: отсутствующий конфиг не должен превращаться в неожиданное поведение. **Механизм сдан, политика — нет**: безопасная зона это механика мира, а Конституция §15 требует сначала ответить на 15 вопросов. Четыре, которые сильнее всего меняют замысел, лежат в `skymp/config/safe-zones.example.json` — главный из них: должен ли город под перемирием быть безопасной зоной или это IC-договорённость, которую поддерживает стража (второе рождает историю, первое рождает правило).
- **Сломанный конфиг остаётся инертным и кричит.** Некорректный JSON не превращается ни в «всё — безопасная зона» (это выключило бы бой на сервере), ни в «ничего ею не является» молча; неизвестная категория внутри зоны игнорируется с ошибкой в лог — категория, которой нет, это правило, которое автор считает созданным, а его нет, — а зона, которая ничего не запрещает, отбрасывается.
- **Без корректных `pos`/`radius` зоной становится вся ячейка.** Это грубо намеренно: «вся таверна» — решение, в котором проще не ошибиться, чем в радиусе в единицах Skyrim, и оно не требует ничего измерять в игре.
- **Стоимость**: `locationalData` — чтение свойства из серверного кэша, а не поход в Papyrus, поэтому оно не платит 13–35 мс, измеренных Red House. Именно поэтому его можно спрашивать на каждое действие без отдельного бюджета.
- **Ни один нынешний вызывающий код не изменил поведение**, и на это есть тест: проверка места происходит только когда вызывающая сторона передаёт `context.actorId`, а ни один из четырёх существующих вызовов его не передаёт. Регрессия здесь включила бы безопасные зоны на всём сервере без чьей-либо просьбы.

#### 1.4.8 Табличка с именем (`nametag-service.js`) и раскрытие личности стаффом
Модуль `nametag` (`ENABLE_NAMETAG_SERVICE`), фаза `lab`, **выключен по умолчанию**. Прототип таблички над головой — недостающая ступень из [`technical/NAMETAG_IDENTITY_SYSTEM.md`](technical/NAMETAG_IDENTITY_SYSTEM.md).

- **Проекция мир→экран выполняется на клиенте, а не на сервере.** `worldPointToScreenPoint` — нативная функция самого игрового процесса, вызываемая сниппетом, который сервер внедряет через `mp.makeProperty`/`updateOwner`. Историческая блокировка — «табличка на каждом кадре положит сервер» — исходила из замеров Red House (13–35 мс на вызов Papyrus), а это **путь туда-обратно по сети** между сервером и клиентом. Этот путь так не платит, поэтому аргумент, блокировавший фичу, к нему не применим.
- **Две частоты, потому что это две разные величины.** Имя и цель — каждые 2 с (тот же тик, что и у голоса: имя меняется, только когда кто-то представился); позиция на экране — до 20 Гц на клиенте, потому что при 2 с табличка выглядит не запоздавшей, а сломанной. Не покадрово: стоит не проекция, а `executeJavaScript`, пересекающий границу CEF — **не измерено**, поэтому значение по умолчанию консервативное.
- **Одна табличка — у ближайшего.** Десять доказали бы то же самое и в десять раз умножили бы неизмеренную стоимость CEF.
- **Внутри не вызывает `getDisplayName()`** — это требование, а не удобство. Когда маскировка станет ступенью той функции, табличка начнёт показывать замаскированное имя без единой строки изменений.
- **`/revelaridentidade`** (право `reveal_identity`, `admin` и `owner`) — **явная команда, а не пассивное состояние**: у «стафф всегда видит настоящее имя» нет события для аудита, а правило лестницы отображения аудита требует. Модератору не выдаётся, потому что раскрытие — единственное действие стаффа, которое **не отменяется**: кик заканчивается на переподключении, золото возвращается другим `/setgold`, `/permakill` — мягкое удаление; раскрытая личность живёт в голове того, кто её прочитал. В `character_known_identities` не пишет: это IC-знание, и запись заставила бы стафф навсегда звать цель настоящим именем в чате.

⚠️ **Проекция ни разу не выполнялась.** `worldPointToScreenPoint` никогда не вызывалась — то, что она достижима этим путём, — **вывод**, а не наблюдение. Соглашение об осях не проверено, точка за камерой — известная дыра, стоимость на 20 Гц не измерена, и никто не проверял с двумя клиентами. Это имеет тот же вес, что и *«никто ещё не слушал»* для нативного голоса (1.4.4).

Модули `fauna-census` (`ENABLE_FAUNA_CENSUS`) и `corpse-probe` (`ENABLE_CORPSE_PROBE`), фаза `lab`, **выключены по умолчанию**, оба за разрешением `run_world_probe` (`admin` и `owner`). Это Части 1 и 2 из §16 документа [`technical/HOSTILE_MOB_ACTIVATION_DECISION.md`](technical/HOSTILE_MOB_ACTIVATION_DECISION.md); протокол сессии — в [`technical/FAUNA_CENSUS_PROTOCOL.md`](technical/FAUNA_CENSUS_PROTOCOL.md).

**Именно из-за них в `module-registry` десять модулей, а этот раздел описывает восемь механик: ни один из двух механикой не является.** Они не выдают предметы, не меняют состояние персонажа и не входят ни в одну цепочку геймплея. Они существуют, чтобы ответить на два вопроса, которые решают, может ли механика охоты существовать вообще, и должны покинуть registry, как только ответят.

- **`/censofauna` работает только на чтение, и это его единственное правило.** Обходит `mp.getActorsByProfileId(0)`, читает `baseDesc` и дистанцию, агрегирует по record и пишет в `skymp/artifacts/`. **Никакого `callPapyrusFunction` внутри цикла** — и дело не в стоимости (хотя 13–35 мс × сотни акторов хватило бы): инструмент наблюдения, который вызывает функцию движка, перестал быть наблюдением. Дорогое чтение изолировано в `/censofauna alvo <actorId>`, по одному актору за раз.
- **`/sondacadaver <actorId>` пишет, и поэтому у него отдельный флаг.** Четыре шага — прочитать, очистить, **перечитать**, восстановить. Третий отделяет *«`mp.set` не бросил исключение»* от *«`mp.set` сработал»*: API, которая принимает вызов и молча игнорирует значение, — самый вероятный случай из всех и единственный, который проверка исключений никогда бы не поймала. Четвёртый возвращает мир в прежнее состояние и доказывает запись дважды.
- **Двойной независимый отказ: зонд никогда не трогает инвентарь игрока.** `getActiveCharacterData` покрывает тех, у кого персонаж загружен; обход `profileId` 1..50 покрывает тех, кто подключился и ещё не выбрал. Каждая проверка по отдельности оставила бы окно — а `mp.set(id,'inventory',{entries:[]})` на акторе игрока стирает месяцы вещей, прошедших через `transaction-service`.

⚠️ **Ни один из двух не запускался.** `mp.get(id,'inventory')` и `mp.set(...)` имеют статус **[DOC]** (`technical/SKYMP_UPSTREAM_REFERENCE.md` §2.5) и никогда не использовались этим проектом — **неизвестен даже формат возврата**, поэтому отчёт записывает его дословно. Тот же вес, что *«ещё никто не слышал»* имеет для голоса (1.4.4), а невыполненная проекция — для таблички (1.4.8).

### 1.5 Клиентский лаунчер (`apps/launcher`)
Сделан на **Electron / React**. Полные подробности в `docs/technical/LAUNCHER_DISTRIBUTION.md`.
- **Обновления** клиента и модпака приходят из **GitHub Releases** (`VITE_GITHUB_DIST_REPO`), с обязательным SHA-256 — манифест без хеша прерывает установку, а не ставит без проверки. Приходят не из `apps/web`: `GET /api/launcher/manifest`, который там был, оказался заглушкой с фальшивым хешем, которую никто не потреблял, и его убрали.
- **Паритет в момент подключения** (`verify-mods` + `analyze-plugins`) сверяет хеш каждого файла в `Data/` и проверяет мастера/порядок загрузки против `http://<SERVER_IP>:<VITE_API_PORT>/mods.json`. Этот эндпоинт обслуживает `apps/game-api` (см. 1.3.1) — когда этот документ говорил, что его не существует, это было правдой: лаунчер стучался в порт без сервиса, и шаг всегда падал как «сервер офлайн». Сервис появился 05.08.2026. **Против собранного лаунчера он ещё не проверялся**, только автотестами.
- **Вход**: лаунчер лишь получает `code` от Discord; обмен на токен делает веб-панель (`POST /api/launcher/oauth/exchange`), потому что любой секрет, вшитый в приложение, раздаваемое игрокам, можно вытащить из инсталлятора.
- Конфигурация приходит из переменных `VITE_*`, вшитых **на этапе сборки** через `define` в `vite.config.ts` — со стороны собранного приложения `.env` не существует.

## 2. Поток принятия решений (золотое правило)

На нашем сервере власть никогда не делегируется клиенту.

**Пример потока (рыбалка или кузнечное дело):**
1. Игрок (клиент) нажимает кнопку взаимодействия.
2. Игровой режим (сервер) получает запрос и проверяет в базе, есть ли у него удочка/ресурс и нужный навык.
3. Сервер меняет базу, сохраняет новый предмет.
4. Сервер вызывает `mp.callPapyrusFunction` только для того, чтобы клиент проиграл анимацию и показал визуальное уведомление об успехе.
*(Если локальный мод попытается пропустить шаг 2, он молча провалится, защищая экономику.)*

Техническая детализация этого правила — что мод может и чего не может трогать, почему Papyrus-скрипты модов не создают состояния, и контракт FormID, требующий паритета порядка загрузки, — в [`MODS_AND_GAMEMODE_CONTRACT.ru.md`](technical/MODS_AND_GAMEMODE_CONTRACT.ru.md).
