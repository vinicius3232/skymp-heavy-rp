## 2. Находки

### 2.1 🔴 Лаунчер не загружал вообще никакой конфигурации — *исправлено*

`electron/main.ts` читал `process.env.VITE_DISCORD_CLIENT_ID`, `VITE_SERVER_IP`, `VITE_API_PORT`, `VITE_GITHUB_DIST_REPO`. **Ничто не клало эти значения в `process.env`**: не было ни `dotenv`, ни `loadEnv`, ни `define` в `vite.config.ts`. Vite грузит `.env` в `import.meta.env` (renderer), а не в основной процесс Node — а у собранного приложения `.env` рядом нет.

Следствие: всё падало в пустой фолбэк или `127.0.0.1`. Вход через Discord невозможен (`client_id=''`), сервер всегда localhost, апдейтер выключен. `.env.example` документировал семь переменных, которые никогда ни на что не влияли.

**Исправлено:** `vite.config.ts` теперь использует `loadEnv` + `define`, подставляя эти обращения на этапе сборки — единственный механизм, переживающий упаковку.

### 2.2 🔴 Client secret Discord вшит в инсталлятор — *исправлено*

`VITE_DISCORD_CLIENT_SECRET` использовался прямо в обмене `code` на токен внутри лаунчера. Исправление одного только 2.1 **сделало бы хуже**: секрет стал бы встраиваться в бандл и раздаваться каждому игроку, скачавшему инсталлятор.

**Исправлено:** обмен переехал в `POST /api/launcher/oauth/exchange` на веб-панели, которая и так хранит секрет. Лаунчер шлёт `{code, redirect_uri}` и получает только публичный профиль — даже не access token. Панель проверяет `redirect_uri` по списку разрешённых, с ограничением частоты.

### 2.3 🔴 Одобрение вайтлиста воскрешало окончательно погибшего персонажа — *исправлено*

`PATCH /api/whitelist/:id` выполнял `UPDATE characters SET status='approved'` с соединением по аккаунту, **без фильтра по статусу**. Игрок, получивший `/permakill` (`status='retired'`), подавший новую заявку и одобренный, получал отставленного персонажа обратно в `approved` — отменяя последствие и стирая эффект записи аудита.

**Исправлено:** `AND c.status='pending'` в `UPDATE` (и в том, что пишет `extra_review_notes`).

### 2.4 🟠 `.env` вне `.gitignore` в двух приложениях — *исправлено*

У `apps/web` и `skymp/gamemode` был собственный `.gitignore`, покрывающий `.env`. **У `apps/bot-discord` не было `.gitignore` вообще** (а там живут `DISCORD_BOT_TOKEN` и `INTERNAL_API_SECRET`), а `apps/launcher` игнорировал `*.local`, но не `.env`. Ни один настоящий `.env` не был закоммичен, но одного `git add .` хватило бы.

**Исправлено:** правило `.env` / `!.env.example` в корневом `.gitignore`, покрывающее все четыре.

### 2.5 🟠 `electron/` никогда не проверялся типами — *исправлено*

`tsconfig.node.json` включал только `vite.config.ts`; `tsconfig.app.json` — только `src`. `npm run build` запускает `tsc`, но `tsc` не смотрел на основной процесс — а `vite-plugin-electron` использует esbuild, который транспилирует без проверки типов. Ошибка типа в `main.ts` (1200+ строк, самая сложная часть лаунчера) уезжала прямо в инсталлятор.

**Исправлено:** `electron` добавлен в include. Проверка поймала мёртвый импорт с первого запуска.

### 2.6 🟠 Три расходящиеся таблицы радиусов близости — *исправлено*

`rp-chat-service.js` (450/1200/1500/2000/3500), `voip-service.js` (200/1200/3000) и `server-options.*.example.json` (350/1400/3000) противоречили друг другу. Эффект для отыгрыша: тот, кто был в радиусе **написанного** шёпота, оказывался вне радиуса **сказанного** — один и тот же жест «подойти ближе» работал или нет в зависимости от канала.

**Исправлено:** `core/proximity-ranges.js` как единый источник; чат, голос и радиус свидетелей смерти выводятся из него.

### 2.7 🟠 Мёртвый эндпоинт манифеста с поддельным хешем — *исправлено*

`GET /api/launcher/manifest` в панели возвращал `hash: "dummy_hash_for_testing"` и фальшивый URL. **Его не потреблял никакой код** — лаунчер использует GitHub Releases. Хуже того: `MANIFEST_VS_NEXUS_COLLECTIONS.md` подробно рассуждал об этом эндпоинте как о настоящем механизме и приписывал SHA-256 пути кода, который использует MD5.

**Исправлено:** эндпоинт удалён; документация переписана как `LAUNCHER_DISTRIBUTION.md`, описывающий каналы, которые существуют на самом деле.

### 2.8 🟠 `/api/apply` без валидации входа — *исправлено*

Принимал пустое имя, биографию из одного символа или текст длиннее колонки (превращавшийся в 500 без объяснений). Поля, которые рубрика вайтлиста считает решающими (мотивации, слабости, социальные связи), были `required` только в HTML — обойти тривиально.

**Исправлено:** валидация на сервере с минимумами и максимумами по каждому полю.

### 2.9 🔴 На порту 7758 не было сервера — *решено, с одним хвостом*

Лаунчер вызывает `http://<SERVER_IP>:7758/mods.json` (паритет модпака) и `/api/queue/status` + `/api/queue/join` (очередь). **Ни один сервис этого репозитория не слушал этот порт.**

Это значит, что проверка паритета модов — то, на чём держится весь контракт FormID и правило власти сервера, — **никогда не выполнялась**.

**Решено:** `apps/game-api` обслуживает все три эндпоинта, с генератором манифеста (`scripts/generate-mods-manifest.js`) и 24 тестами. Подробности в `LAUNCHER_DISTRIBUTION.md`. Заодно пришёл пункт 1.1b: очередь теперь требует тикет, выпущенный панелью, вместо `discordId`, который сообщает клиент.

**Хвост — решён нативным путём:** изучение `skymp5-server/ts/systems/login.ts` показало, что SkyMP решает это сам. При `offlineMode: false` он не читает `profileId` клиента: он разрешает `gameData.session` через мастер-API и берёт пришедший оттуда `id`.

`apps/web` стал обслуживать этот контракт (`GET /api/servers/:masterKey/sessions/:session`), `apps/game-api` пишет сессию в `game_sessions` (миграция v8) при допуске из очереди, а лаунчер уже записывает токен как `session`. Итог: `whitelist.js` не пришлось менять — приходящий `profileId` **и есть** проверенный `accountId`.

Из-за этого построенный нами `/internal/session/resolve` стал избыточен. Он остаётся в `game-api` только до тех пор, пока тест в игре не подтвердит нативный поток.

### 2.10 🟡 `server-options.json` никто не читал — *решено частично*

`Initialize-LocalConfig.ps1` создаёт файл, `SERVER_OPTIONS_SCHEMA.md` документирует 112 строк опций, а **код не читает ничего**. Конфигурация, которая выглядит существующей и ничего не делает, хуже отсутствующей: кто-то настроит `permadeathEnabled` или `startingGold` и решит, что сервер сломан.

**Решено:** `core/server-options.js` загружает, валидирует и применяет. Восемь опций подключены по-настоящему (радиусы чата/голоса, `oocEnabled`, ограничение частоты, `permadeathEnabled`, `playerRespawnSeconds`, `startingGold`) — остальные остаются инертными, но загрузчик теперь **предупреждает при старте**, когда находит такую в файле, и **прерывает загрузку**, если значение неверного типа или вне диапазона.

Принятый принцип: в `SPEC` попадает только опция, которая действительно меняет поведение. Объявить все 24 и подключить 8 воссоздало бы ту же проблему, только менее заметную — ведь тогда файл *читается*, и у человека меньше причин что-то подозревать. Есть тест, не дающий примеру обзавестись новым ключом без классификации. 18 тестов в `core/server-options.test.js`.

### 2.11 🟡 У `apps/web` не были установлены зависимости и не было тестов — *решено*

`node_modules` отсутствовал. `Start-AllServices.ps1` проверял только наличие `.env`, поэтому панель умирала на `require('dotenv')` в отдельном окне, а оркестрация рапортовала об успехе. Это был также единственный сервис с бизнес-логикой (авторизация администрации, одобрение вайтлиста, обмен OAuth) **вообще без тестов**.

**Решено:** зависимости установлены; 29 smoke-тестов в `server.test.js` (страж аутентификации на 12 маршрутах, валидация заявки, список разрешённых `redirect_uri`, хеш тикета); `Start-AllServices.ps1` теперь заранее проверяет вход, `.env` и `node_modules` каждого сервиса и сообщает, что не поднялось, вместо того чтобы врать «завершено».

### 2.12 🟡 Бот Discord не регистрировал команды автоматически — *решено*

`/voz-criar` и `/voz-fechar` появлялись только после ручного `npm run deploy-commands`. Никто не предупреждал, если про это забыли; команда просто не появлялась в Discord.

**Решено:** `deploy-commands.js` стал модулем и выполняется по событию `ready` бота. Сбой там **не роняет бота** — синхронизация вайтлиста критична и работает без голосовых команд, — но громко пишет в лог, что именно не появится. Продолжает работать отдельно (`npm run deploy-commands`), где уже выходит с кодом ошибки. 6 новых тестов.

### 2.13 🔴 Два несовместимых способа вызывать Papyrus — *решено доказательством из upstream*

Найдено при типизации API `mp` (`skymp/gamemode/types/mp.d.ts`). Параметр `self` у `mp.callPapyrusFunction('method', ...)` передавался двумя разными способами в одном и том же коде:

| Форма | Где |
|---|---|
| `{ type: 'form', desc: mp.getDescFromId(actorId) }` | `death-service.js`, `player-panel-service.js` — **2 файла** |
| сырой `actorId` (`number`) | **22 места**, включая `core/transaction-service.js`, `inventory-service.js`, `npc-cleaner.js`, `governance-service.js`, `market-stalls-service.js` |

Обе появились в **одном коммите** (`82625d2`, 11.07.2026): миграции с одной на другую не было, это несогласованность с самого начала. Документация SkyMP формат не оговаривает, и ни одна из форм не проверялась в игре.

**Почему это серьёзно:** если валидна только объектная форма, 22 вызова падают молча — а среди них выдача предмета в `core/transaction-service.js`. База записала бы транзакцию корректно, а инвентарь игрока остался бы пустым. То же касается удаления NPC (`npc-cleaner`), синхронизации инвентаря при спавне (`inventory-service`) и кандалов управления (`SetActorValue SpeedMult`).

**Решено:** поиск в upstream нашёл `misc/tests/` — девять интеграционных тестов, работающих против настоящего сервера. **Все они используют исключительно объектную форму**, в том числе для аргументов-ссылок. Это перестало быть догадкой.

22 вызова переведены, с хелпером (`core/papyrus.js`: `actorRef`/`baseRef`), чтобы не повторять конструкцию. Существующие тесты эти пути не задевали (моки не определяют `mp`, поэтому их защищали guard'ы `typeof mp === 'undefined'`) — поэтому `core/papyrus.test.js` стал смотреть на **переданный аргумент**, а не только на результат. 5 новых тестов.

Проверить в игре по-прежнему стоит, но уже как подтверждение, а не как расследование.

### 2.14 🟡 PARKED-модули вызывают `hasPermission` с числом — *решено в корне*

`admin-service.hasPermission(actorId, permission)` делает `staff.permissions.has(permission)`, где `permissions` — это `Set` **строк**. Двенадцать вызовов передают число (уровень администрации: `10`, `20`):

`crafting-service` (2), `disguise-service` (1), `economy-regional` (1), `faction-service` (4), `justice-service` (4)

`Set.has(20)` на Set строк всегда `false`, поэтому **любая** проверка прав в этих модулях всегда отказывает. Сегодня влияния нет — все пять в PARKED, — но это значит, что они сломаны сильнее, чем «просто не зарегистрированы»: включение флага не заставило бы их работать, а лишь заблокировало бы внутри них все действия администрации.

**Решено:** вместо латания 12 вызовов в коде, который не работает, `hasPermission` стал проверять собственный аргумент. Числовой уровень и несуществующее имя права теперь **отказывают и пишут ошибку в лог** со списком допустимых значений.

Осознанный выбор не бросать исключение: оно уронило бы команду игрока из-за ошибки программиста. Отказ — безопасный результат; лог — то, что заставит кого-то исправить. Это ловит и обратный случай: тот, кто пишет `hasPermission(id, 'manage_factions')`, думает, что создал правило, а создал дверь, которая никогда не откроется. 4 новых теста.

**Закрыто и в корне, и в листьях 07.08.2026.** Двенадцати вызовов больше нет: `disguise-service`, `faction-service` и `justice-service` удалены, а три оставшихся (`/addrecipe`, `/addingredient`, `/settax`) перешли на именованные права — `manage_recipes` (новое) и `set_gold`. Рассуждение о том, какое право требует каждая команда, — в [§7.4 `PARKED_SERVICES_DECISION.md`](PARKED_SERVICES_DECISION.md); статическая проверка в `parked-staff-permissions.test.js` падает, если любой продакшен-файл геймода снова начнёт передавать число.

## 2-bis. Второй проход (06–07.08.2026)

Первый проход читал код. Этот **поставил сервер и включил его**, и разница видна по тому, какие дефекты находит каждый: девять из десяти ниже — конфигурация или жизненный цикл, то есть класс, до которого юнит-тест не дотягивается, потому что нечего тестировать в файле, который никто не читает.

### 2.15 🔴 Клиент с лишним плагином проходил проверку паритета — *исправлено*

Найдено при выносе логики лаунчера в тестируемый вид. Обе проверки паритета шли по **списку сервера** и спрашивали «есть ли это у игрока?». Ни одна не шла по списку игрока и не спрашивала «знает ли сервер про это?».

Следствие: клиент со **всеми** нужными модами, с правильным хэшем, **плюс один лишний `.esp`**, проходил обе. А лишний плагин в load order занимает индекс и сдвигает все последующие — `HeavyRP.esm`, который на сервере `02`, у него становится `03`, и **каждый `base_id`, записанный в базе, начинает указывать на другую запись на экране этого игрока**.

Это ровно тот отказ, ради предотвращения которого существует контракт FormID (`MODS_AND_GAMEMODE_CONTRACT.md` §3), и он не даёт никакой ошибки: он даёт сундук с другим содержимым.

Вместе с этим нашёлся второй случай: когда сервер не сообщал load order, код откатывался на **локальный** — сравнивал игрока с самим собой и всегда отвечал `ok`. Худший из возможных ответов, потому что выглядит как одобрение.

**Исправлено:** логика вынесена в `apps/launcher/electron/parity.mjs` (без `fs`, без `http`, без `electron`), 24 теста. Проверка теперь идёт в обе стороны, использует `plugins.txt`, чтобы знать, что включено на самом деле (присутствующий, но отключённый плагин ничего не сдвигает), а отсутствующий load order теперь **не проходит**.

### 2.16 🔴 Гейммод никогда не загружал собственный `.env` — *исправлено*

`dotenv` был в `dependencies`, `.env.example` существовал, и `CONTRIBUTING.md` §1 вместе с `FASE_0_ROTEIRO.md` велели заполнить `skymp/gamemode/.env`. **Ни один файл гейммода не вызывал `require('dotenv')`** — этот файл читал `apps/web/server.js`, для себя, и именно это делало сбой невидимым.

Следствие: `module-registry.bootAll()` всегда видел `process.env[ENABLE_*]` неопределённым, поэтому управление, лавки, смерть, панель и VOIP были выключены навсегда. Без ошибки — лог писал `DESATIVADO (... не определено)`, ровно то же, что написал бы, если бы человек сам их выключил.

Проверка `flags de ambiente` всё это время давала `[PASS]`, потому что сверяла только наличие строки в `.env.example`: она доказывала, что кто-то написал строку, а не что включение строки что-то делает.

### 2.17 🔴 Роль стаффа переживала отключение — *исправлено*

`admin-service.removeStaffRole` существовала, экспортировалась и имела тест, и **ни один продакшен-путь её не вызывал**. Кэш ключуется по `actorId`, который SkyMP переиспользует между сессиями, а `registerStaffRole` работает только при входе: тот, кто попадал на `actorId` ушедшего админа, наследовал `ban`, `set_gold` и `retire_character`.

В тестах прав это не всплывало, потому что роль была верна в оба момента — дефект был про сессию, а не про авторизацию.

### 2.18 🔴 `npc-cleaner` удалял ключевых NPC и реализовывал отвергнутый вариант — *исправлено*

Он обходил `mp.getActorsByProfileId(0)` и вызывал `disable` **и `delete`** на каждом акторе, пропуская лишь тех, кто был в allowlist — а она была пуста. Торговцы, стража и квестовые NPC, каждые 60 с, и `delete` на персистентной ссылке не отменяется.

`NPC_POLICY_DECISION.md` взвесил три варианта и выбрал **C (выборочный спавн)**; код реализовывал B, отвергнутый, в самой крайней форме. Вдобавок `safeRadius` был объявлен с комментарием «чистит только NPC вдали от игроков» и **никогда не читался**.

Список стал списком блокировки (пустой = не удаляет ничего), радиус начал существовать, а `delete` убран.

### 2.19 🟠 `/setgold` был единственным денежным путём мимо реестра — *исправлено*

Голый `UPDATE characters SET gold = ?`, без транзакции и без строки в `gold_transactions` — тот самый шаблон, из-за которого удалили `economy-service.js`. Это команда, которой след нужен больше всех: золото без записанного происхождения неотличимо от дублирования из-за бага, а сделать это может как раз стафф.

Заодно добавлен недостающий guard: `/setgold <id>` без значения передавал `NaN`, который MySQL пишет как `0`, — опечатка молча обнуляла состояние игрока.

### 2.20 🟠 Покупка в лавке переизобретала `transaction-service` — *исправлено*

`buyItem` писал SQL для золота и инвентаря вручную. Он был атомарным и с реестром, то есть небезопасным не был; он был второй реализацией вне файла, который существует, чтобы быть единственной, — с продублированными `FOR UPDATE` и защитой от отрицательного баланса.

Публичные функции сервиса задачу не решали (каждая открывает свою транзакцию, а покупка обязана коммитить остаток, золото, налог и предмет вместе). Внутренние примитивы — которые уже принимали соединение — теперь экспортируются как `tx.*`, с явным контрактом.

У `buyItem` **не было ни одного** поведенческого теста; появилось 10.

### 2.21 🔴 `characters.gold` не существовала в мигрированной базе — *исправлено (миграция v9)*

Колонка объявлена в `schema.sql` и **ни в одной миграции**. Свежая база работает; тот, кто создал свою до появления колонки и применил `v2`→`v8` по порядку, как велит CONTRIBUTING, её не получает никогда. v2 при этом создаёт `gold_transactions` — сам реестр — не гарантируя колонку баланса, за которой он следит.

Загрузку это не ломает: ломает первую операцию с золотом, а это весь `transaction-service`. По сценарию Фазы 0 тест умер бы на **шаге 5.6**, после пяти удачных шагов, с двумя людьми и запущенным Skyrim.

Найдено через `npm run check:schema` (пункт 4.1 плана) — ровно тот класс проблем, ради которого он написан.

### 2.22 🟠 `core/soul.js` хранил два невидимых символа со смыслом — *исправлено*

Файл считался бинарным для `grep` и для `file`. Причина была не та, что казалась: помимо сырого класса комбинирующих знаков в `normalize()`, там был **байт NUL** в разделителе подписываемого материала, который на экране читается как `].join('')`.

NUL — **правильный** выбор (он не переживает `normalize()`, поэтому ни один игрок не впишет его в заявку; с набираемым разделителем `'ab'+'c'` и `'a'+'bc'` подписали бы один материал, и две разные заявки родились бы с одной душой). Проблема была в невидимости: любой редактор, вычищающий управляющие символы при сохранении, изменил бы семя **всех уже выведенных душ**.

Проверено, что сёмена не изменились, а вывод получил тест на золотые значения.

### 2.23 🔴 Два дефекта, которые вскрыл только первый реальный запуск — *исправлены*

**`Cannot find module 'dotenv'`, и гейммод не загружался.** SkyMP копирует входной файл в `%TEMP%` и запускает оттуда — это написано в шапке самого файла, и именно поэтому все require в нём используют абсолютный путь. У dotenv, добавленного при исправлении 2.16, спецификатор был голым, а голый спецификатор разрешается от каталога исполняемого файла.

Он прошёл 366 тестов и CI, потому что оба запускаются из `skymp/gamemode/`. **Это самый чистый пример того, о чём шапка `ci.yml` уже предупреждала:** *«зелёный CI значит, что вы не сломали то, что уже проверялось, а не что оно работает в игре»*.

**Ни одна игровая опция не читалась.** `.env.example` задавал `NODE_ENV=development`, загрузчик собирает `server-options.<NODE_ENV>.json`, а в проекте есть только `local` и `production`. Правка `permadeathEnabled`, радиусов чата или `startingGold` не делала ничего.

### 2.24 🟡 У `database.js` не было `close()` — *исправлено*

`verify-governance-market-stalls.js` уже вызывал `db.close()` за guard'ом, а функции никогда не было: guard не срабатывал, и пул mysql2 держал event loop. `RUN_DB_CHECK=1 npm run test:systems` печатал `10/10 passaram` и **висел вечно** (exit 124 по таймауту; теперь exit 0). В CI с базой задача завершилась бы только по таймауту, и отчёт сказал бы «отменено».

### 2.25 🟠 PARKED-модуль можно было включить в обход реестра — *исправлено*

`governance-service` решал, работает ли `economy-regional`, читая `process.env.ENABLE_REGIONAL_ECONOMY` напрямую, в двух местах: одного флага хватало, чтобы загрузить и **выполнить** запаркованный модуль без разрешения зависимостей, без регистрации команд и без shutdown. `CONTRIBUTING.md` §3.3 запрещает ровно это, как и раздел «Не делать» этого отчёта.

### 2.26 🟡 У генератора `mods.json` не было теста — *исправлено*

При том что именно он решает контракт FormID — то, что при ошибке не даёт ошибки: даёт сундук с другим содержимым. Появилось 6 тестов и флаг `--only-load-order`, позволяющий пройти Фазу 0 до появления модпака: без него генерация манифеста из рабочей `Data/` даёт файл, требующий машину того, кто его сгенерировал.

## 4. Чего этот отчёт не покрывает

- **Поведение в игре.** Ни одна команда (`/painel`, `/socorrer`, `/iniciar`, `/permakill`, `/voz`) не выполнялась в реальной сессии. Тесты используют замоканный `mp`.
- **Реальное взаимодействие с API Discord.** Бот и новый маршрут OAuth не проверялись против настоящего бота/сервера Discord.
- **Собранную сборку лаунчера.** Исправление `define` проверено типизацией, а не сгенерированным инсталлятором.
- **Нагрузку.** Никаких измерений с несколькими игроками, а именно там опрос каждые 2с в `death-service`/`player-panel`/`voip` проявится первым.
